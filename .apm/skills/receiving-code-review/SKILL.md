# コードレビューの受領

コードレビューには感情的な演技ではなく、技術的評価が必要です。
実装前に検証し、仮定の前に質問し、社会的な快適さより技術的正しさを優先します。

## 応答フロー

1. READ: 反応せずにフィードバックを最後まで読む
2. UNDERSTAND: 自分の言葉で要件を言い換える（または質問）
3. VERIFY: コードベースの現実と照合する
4. EVALUATE: このコードベースにとって技術的に妥当か判断する
5. RESPOND: 技術的な了承、または理由付き pushback
6. IMPLEMENT: 1 件ずつ、それぞれテストを添えて実装

## 不明確なフィードバック

不明な項目がある場合は実装前に明確化を求める。項目は関連していることがあり、
部分的な理解は誤った実装を生む。

## 検証ポイント

外部レビュアーの提案は評価すべき提案であり、従う命令ではない。

- このコードベースにとって技術的に正しいか
- 既存機能を壊さないか
- 現実装の理由は何か
- 全プラットフォーム / バージョンで動くか
- レビュアーは全体コンテキストを理解しているか

## push back するタイミング

- 提案が既存機能を壊す
- レビュアーがコンテキスト不足
- YAGNI 違反（未使用機能）
- このスタックにとって技術的に誤り
- legacy / 互換性の理由がある
- アーキテクチャ判断と矛盾する

push back は防御ではなく技術的理由で行う。具体的な質問、動く test / code を参照する。

## 実装順序

複数項目がある場合:
1. 不明な項目を先に明確化
2. Blocking issues (breaks, security) → Simple fixes → Complex fixes の順
3. 各修正を個別にテスト
4. regression がないことを確認

## GitHub スレッド返信

GitHub の inline review comment に返信するときは、トップレベル PR コメントではなく
コメントスレッド（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`）で返信する。
