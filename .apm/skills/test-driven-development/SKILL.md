# テスト駆動開発（TDD）

変更する契約をテストで示し、期待した理由で失敗することを確認してから実装します。
テストは実装の形ではなく、利用者や呼び出し元が観測する挙動を検証します。

## 適用範囲

- 新機能・挙動変更・バグ修正は、実装前の RED → GREEN で回帰検出力を確認します。
- 挙動を維持するリファクタリングは既存の回帰テストを先に確認し、守る契約の不足分だけ追加します。
- 可逆で挙動を変えない文書・軽微な設定変更は、既存の format・schema・参照・同期検査を使います。検出力を増やさないテストの追加や、TDD を使わないことだけを理由とする再承認は不要です。
- 設定変更でも権限・保存・実行時の挙動が変わる場合は、その契約と境界に対応する検証を行います。
- 生成物は原本を修正し、生成・同期の検査で確認します。

## RED → GREEN → REFACTOR

1. **契約を確認する。** 要件、既存の実コード・テスト・fixture から、入力と観測可能な結果を特定します。バグは本番に近い操作経路で再現します。
2. **RED を確認する。** 変更する挙動を示す最小のテストを書き、現在の実装で期待どおり失敗することを確認します。構文・import・環境エラーは RED の証拠にしません。
3. **GREEN にする。** 契約を満たす最小の実装を行い、同じテストと影響する既存テストを実行します。失敗を隠すために assertion や契約を弱めません。
4. **必要な整理を行う。** GREEN を保って重複や命名を改善します。新しい挙動は別の RED から扱います。

テストが最初から通る場合は、既存の保証か再現不足かを調べます。失敗させるためだけにテストを壊さず、既存の保証は再利用します。
実装が先に存在する場合は、ユーザーや他者の変更を保全し、隔離した修正前の状態や対象差分の一時退避で RED を確認してから戻します。作業時間や手順違反を理由にコードを一律削除しません。

## 境界とテストの選択

- 入力・権限・ストレージ・ブラウザ API・ユーザーデータの境界では、正常系に加えて該当する拒否・エラー・端の値を検証します。
- 保存の修正では、保存後の close / reload / 再読み込みなど、問題が現れる実際の境界まで確認します。mock の呼び出し回数だけで永続化の成功を主張しません。
- 既存の helper と fixture を優先し、mock は外部依存など必要な境界に限ります。実装の写しや文言一致だけのテストを追加しません。
- 変更に最も近いテストから実行します。TABBIN の node / DOM / 全体検査の選択は `$test-selection` に従います。

mock やテスト用 helper の設計で迷う場合は [testing-anti-patterns.md](testing-anti-patterns.md) を参照します。

## 完了の証拠

変更した挙動、RED の失敗理由、GREEN の結果、確認した境界を簡潔に記録します。未実行の検査や環境による失敗は、通過した検査と区別します。
品質・coverage ゲートと commit / push / PR の許可境界は、[repository-guidelines](../../../.apm/instructions/repository-guidelines.instructions.md) を source of truth とします。
