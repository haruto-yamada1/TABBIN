# 計画の実行

計画の目的、守る契約、対象ファイル、検証条件を確認して実行する。
ハーネス run がある場合はその状態を更新し、別の計画を重ねない。

## 実行と継続

- 計画と現状を照合する。仕様や許可を変える欠落は明確化し、それ以外の実装判断は既存パターンに沿って進める。
- 依存関係と変更範囲で作業を区切る。一律に3タスクごとのバッチを作らない。
- タスクに必要な編集・検証を行い、結果と残る問題を短く報告する。
- 実装全体が依頼済みなら、報告後も次の作業へ続ける。ユーザーが指定した承認チェックポイントでは回答を待つ。
- テスト失敗や不足依存は原因を調べ、許可範囲内で修正する。失敗しただけでユーザーに判断を戻さない。
- 未提供の情報・権限・外部状態が必要で進めない場合は、試したことと不足条件を示す。独立した作業は続ける。
- 途中の質問には短く答え、計画の目的を維持する。方向転換の依頼は計画へ反映する。

## 完了

現在の差分に必要な検証とリポジトリの完了ゲートを満たす。
同じ差分・環境の成功証拠は再利用し、未実行のチェックは通過と書かない。
公開が依頼済みなら $commit-push-pr の手順へ進む。
統合方法の判断が必要な場合だけ $finishing-a-development-branch を使う。
ローカル修正だけの依頼なら、差分と検証結果を報告して完了する。

隔離が必要な作業では $using-git-worktrees、独立タスクの分担には
$subagent-driven-development を使う。定型の選択肢提示を完了条件にしない。
