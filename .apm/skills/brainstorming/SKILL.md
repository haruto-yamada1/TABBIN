# アイデアを設計へ

目的、制約、成功基準を整理し、実装を左右する選択肢を決める。
仕様が明確な修正や既存パターンに沿う設定変更は直接実装する。
ハーネスの計画や既存の実装計画がある場合は、その計画を使う。

## 進め方

- 対象のコードと契約を必要な範囲で確認する。全リポジトリの読み込みを前提にしない。
- 会話と既存実装から分かる要件は再質問しない。結果を変える不足情報だけを尋ね、回答に依存しない調査は進める。
- 有意な代替案がある場合に比較し、推奨案と理由を示す。一律に案の数を埋めない。
- 設計は規模に応じて短く示す。データフロー、エラー境界、検証方法など、判断に必要な点を含める。
- ユーザーが設計レビューや段階承認を求めた場合、または仕様・許可範囲を変える判断が残る場合は、その判断に依存する実装を待つ。
- 実装まで依頼され、要件が確定していれば、方針を伝えて実装・検証へ続ける。定型の設計承認を追加しない。

## 記録と引き渡し

長期に残す設計判断は既存の設計文書や ADR に記録する。
一時的な段取りをローカル Markdown TODO の source of truth にしない。
複数工程の計画が必要な場合だけ $writing-plans を使う。

設計を整理する依頼だけでは、実装・commit・push・PR へ進まない。
公開操作は `.apm/instructions/repository-guidelines.instructions.md` の許可境界に従う。
