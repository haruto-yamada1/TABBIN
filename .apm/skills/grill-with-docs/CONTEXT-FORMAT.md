# CONTEXT.mdフォーマット

## 構造

```md
# {コンテキスト名}

このコンテキストが何で、なぜ存在するかの1〜2文の説明。

## 用語

**TabGroup**:
ドメイン単位でまとめられた保存タブのグループ。`id`、`domain`、`urlIds` を持ち、親カテゴリに属する。
_避ける_: ドメインカード、タブセット、タブコレクション

**ParentCategory**:
TabGroupを分類するトップレベルのカテゴリ。名前と所属ドメインIDのリストを持つ。
_避ける_: 親フォルダ、メインカテゴリ、トップカテゴリ

**SubCategory**:
URL単位で付与される子カテゴリ。TabGroup 内の個別URLに `subCategory` フィールドで紐づく。
_避ける_: タグ、ラベル、小分類

**CustomProject**:
ユーザーが独自に作成するプロジェクト単位のURL管理グループ。`projectKeywords` による自動分類に対応。
_避ける_: プロジェクトフォルダ、PJ、ブックマークグループ
```

## ルール

- **意見を持つ。** 同じ概念に複数の言葉がある場合、最適なものを1つ選び、他は `_避ける_` に列挙する。
- **定義は簡潔に。** 最大1〜2文。それが *何* かを定義し、何を *する* かではない。
- **このプロジェクトのコンテキスト固有の用語だけ含める。** 一般的なプログラミング概念（タイムアウト、エラータイプ、ユーティリティパターン）はプロジェクトが頻繁に使っても属さない。用語を追加する前に問う: このコンテキスト固有の概念か、一般的なプログラミング概念か？前者だけが属する。
- **自然なクラスターが形成されたらサブ見出しでグループ化する。** すべての用語が1つのまとまりに属すなら、フラットリストで良い。

## 単一コンテキスト vs 複数コンテキスト

**単一コンテキスト（ほとんどのリポジトリ）:** リポジトリルートに1つの `CONTEXT.md`。

**複数コンテキスト:** リポジトリルートに `CONTEXT-MAP.md` を置き、コンテキスト一覧、場所、相互関係を記載する:

```md
# コンテキストマップ

## コンテキスト

- [saved-tabs](./src/features/saved-tabs/CONTEXT.md) — タブの保存・表示・検索・自動削除
- [options](./src/features/options/CONTEXT.md) — ユーザー設定とプリファレンスの管理
- [ai-chat](./src/features/ai-chat/CONTEXT.md) — AI によるタブ分類・提案チャット
```

スキルはどちらの構造が適用されるか推測する:

- `CONTEXT-MAP.md` が存在する場合、それを読んでコンテキストを見つける
- ルートの `CONTEXT.md` だけが存在する場合、単一コンテキスト
- どちらも存在しない場合、最初の用語が確定したときにルートの `CONTEXT.md` を遅延作成する

複数コンテキストが存在する場合、現在のトピックがどのコンテキストに関連するか推測する。不明な場合は質問する。
