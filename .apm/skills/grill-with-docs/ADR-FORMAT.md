# ADRフォーマット

ADRは `docs/adr/` に置き、連番ナンバーを振る: `0001-slug.md`, `0002-slug.md` など。

`docs/adr/` ディレクトリは遅延作成する — 最初のADRが必要になったときだけ作る。

## テンプレート

```md
# {決定の短いタイトル}

{1〜3文: コンテキスト、何を決定したか、そしてその理由。}
```

これだけ。ADRは1段落でも良い。価値があるのは *何を* 決定したか、そして *なぜ* かを記録することであり、セクションを埋めることではない。

## オプションセクション

本当に価値があるときだけ含める。ほとんどのADRでは不要。

- **Status** フロントマター (`proposed | accepted | deprecated | superseded by ADR-NNNN`) — 決定が再検討されるときに有用
- **検討した選択肢** — 却下された代替案を覚えておく価値があるときだけ
- **影響** — 自明でない下流への影響を指摘する必要があるときだけ

## ナンバリング

`docs/adr/` をスキャンして既存の最大番号を見つけ、1つ増やす。

## ADRを提案するタイミング

以下の3つがすべて満たされたとき:

1. **後戻りが困難** — 後から考えを変えるコストが大きい
2. **文脈なしでは驚き** — 将来の読者がコードを見て「なぜこんなやり方を？」と疑問に思う
3. **本当のトレードオフの結果** — 本当に代替案があり、特定の理由で1つを選んだ

決定が後戻りしやすいならスキップする — そのまま戻せば良い。驚きがなければ誰も疑問に思わない。代替案がなければ「当然のことをした」と記録するだけ。

### TABBINでADRに該当する具体例

- **ストレージ構造の変更。** `chrome.storage.local` のデータスキーマ変更、旧形式（`urls` 直持ち）から新形式（`urlIds` + `UrlRecord` 参照）へのマイグレーション戦略。
- **ウィンドウ/タブの操作モデル。** `removeTabAfterOpen` のデフォルト挙動、「すべて開く」を別ウィンドウにするか現在ウィンドウにするか。
- **ブラウザ拡張の権限設計。** manifest.json で要求する権限の範囲、`tabs` 権限の要不要。
- **カテゴリ分類のアーキテクチャ。** ドメイン単位の `TabGroup` と `ParentCategory` の関係、`SubCategory` のキーワードベース自動分類ロジック。
- **AI統合の方針。** `ollamaModel` のローカルLLM利用、`aiSystemPrompts` のプリセット設計、AIチャットのプロトコル（`ai-chat-protocol.ts`）。
- **データ競合・衝突回避。** 複数ウィンドウからの同時ストレージ更新時の排他制御方式。
- **i18n の粒度。** メッセージキーの命名規則、プレースホルダー方式（`{{variable}}`）の採用理由。
