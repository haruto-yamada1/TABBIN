# 完了前の検証

主張は現在の成果物を裏付ける証拠に合わせる。
実行を試みたことと、成功を確認したことを区別する。

## 必要な証拠

| 主張                     | 確認するもの                                                        |
| ------------------------ | ------------------------------------------------------------------- |
| テスト・lint・build 成功 | 該当コマンドの終了コード、失敗数、結果。別のコマンドで代用しない。  |
| バグ修正                 | 元の症状を再現する検証と、修正後の結果。                            |
| 要件充足                 | 依頼・契約と実ファイルや挙動の対応。テスト成功だけで決めない。      |
| 委任作業の完了           | 担当差分と検証ログ。サブエージェントの自己申告だけで決めない。      |
| push / PR 作成           | 成功結果とremote / PRの現在の状態。ローカルcommitだけで代用しない。 |

## 検証を選ぶ

- 変更に近い検証から始め、`.apm/instructions/repository-guidelines.instructions.md` の必須ゲートを実行する。
- 現在の差分・依存・設定・環境に対する成功証拠は同じセッションで再利用する。回答や skill の切り替えだけを理由に再実行しない。
- 関係する変更、検証の失敗、未解決の懸念があれば、影響する検証を再実行する。
- 読み取りや軽微な文書変更に、実装をなぞるだけのテストを追加しない。対応する構文・参照・同期検査を選ぶ。
- バグの回帰検証は失敗理由と修正後の成功を確認する。RED/GREEN が証明済みなら、完了報告のために修正を戻して再現し直さない。
- 長いログは保存・検索して必要な証拠を読む。全出力を会話へ貼り付けることを検証条件にしない。

## 報告

何を検証したか、結果、未実行または環境で阻まれた項目を簡潔に示す。
focused test の成功を全体ゲートの成功とは書かない。
失敗は原因を調べて対応し、未解決ならその範囲を明示する。
